# Javadoc

Javadoc предназначен в первую очередь для того чтобы разработчик мог понять смысл пакета, класса, метода не вникая и не понимая в Java код.
Javadoc должен понятно **простыми** словами объяснить разработчику зачем нужен тот или иной компонент кода.

Описание общего названачения пакета, класса или метода стоит оформить как Javadoc а не как обычный комментарий.

Javadoc должен объяснять:

- Зачем существует компонент и какую задачу он решает.
- Что компонент делает и какой результат гарантирует.
- Какие условия должны быть соблюдены для его корректного использования.
- Какие последствия имеет его использование.
- Какие ограничения и особенности поведения необходимо учитывать.

Главный принцип: "необходимо документировать контракт и поведение, а не последовательность инструкций"

Необходимо документировать:

- Назначение публичных пакетов в package-info.java.
- Публичные классы, интерфейсы, перечисления (enum), записи (record) и аннотации.
- Публичные и защищённые (public, protected) методы и конструкторы, определяющие контракт API.
- Публичные и защищённые поля, если они являются частью API.
- Компоненты record, если их семантика неочевидна.
- Сложные контракты интерфейсов и абстрактных методов.

## Документация классов

Документация класса должна раскрывать его назначение, ответственность и правила использования, а не просто перефразировать название класса или перечислять его методы.

Документация должна отвечать на вопросы:

- Зачем нужен класс? / Какую задачу он решает?
- За что отвечает класс? / Какова его роль в системе?
- Какие операции и бизнес-правила он обеспечивает?
- С какими сущностями работает? / Как изменяет их состояние?
- Какие ограничения и гарантии необходимо учитывать при его использовании?
- Где заканчивается ответственность класса?

Примеры:

```java
// плохо, так как описание повторяет название класса:
// непонятно, за что отвечает сервис,
// какие задачи решает и какие гарантии предоставляет

/**
 * Сервис подтверждения заказов.
 */
public class OrderConfirmationService {
}


// хорошо, так как раскрывает:
// - назначение класса и его роль в системе;
// - основные обязанности и бизнес-правила;
// - ограничения и гарантии;
// - границы ответственности

/**
 * Обеспечивает подтверждение заказов перед передачей на исполнение.
 * <p>
 * Проверяет доступность позиций заказа и возможность его перехода
 * из {@link OrderStatusEnum#CREATED} в
 * {@link OrderStatusEnum#READY_FOR_EXECUTION}.
 * <p>
 * При успешном подтверждении сохраняет новое состояние заказа
 * и регистрирует {@link OrderConfirmedEvent} в одной транзакции.
 * <p>
 * Не выполняет резервирование товаров и организацию доставки.
 */
public class OrderConfirmationService {
}
```

Javadoc класса должен описывать **общий контракт и ответственность компонента**, а Javadoc методов - конкретные операции, аргументы, результаты и исключения.

Не следует дублировать документацию методов, перечислять внутренние зависимости или описывать последовательность вызовов.

Документируй только те ограничения и гарантии, которые действительно обеспечивает класс.


## Документация методов

Документация метода должна раскрывать смысл операции, а не просто перефразировать её название.

Документация должна отвечать на вопросы:

- Зачем нужен метод? / Какую задачу решает метод?
- Какова его роль в предметной области? / В каких ситуациях его следует использовать?
- Что происходит с переданными атрибутами? / Как атрибуты связаны друг с другом? / Что означают параметры метода?
- Что вернется в ответе? / Какой итог выполнения метода? / Что гарантирует метод?

Примеры:

```java
// плохо, так как описание повторяет имя метода
// и не раскрывает ожидаемое поведение:
// непонятно, что означает подтверждение заказа,
// непонятно, какой заказ допускается подтверждать

/**
 * Подтверждает заказ.
 *
 * @param order заказ
 *
 * @return готовый заказ
 */
Order confirmOrder(Order order);

// хорошо, так как описывает действие и его
// результат в терминах предметной области:
// после подтверждения заказ переходит в состояние,
// допускающее дальнейшее исполнение, 
// понятно какое состояние заказа ожидается на входе
// понятко какие ошибки ожидать и в каком случае

/**
 * Подтверждает заказ и переводит его
 * в состояние готовности к исполнению.
 *
 * @param order заказ в состоянии
 *              {@link OrderStatusEnum#CREATED},
 *              который необходимо подтвердить
 *
 * @return подтвержденный заказ в состоянии {@link OrderStatusEnum#READY_FOR_EXECUTION}
 *
 * @throws IllegalArgumentException если заказ находится в состоянии {@link OrderStatusEnum#CANCELLED}
 * @throws OrderConfirmationException если заказ содержит позиции, недоступные для доставки
 */
Order confirmOrder(Order order);


```

## Документация полей и констант

Javadoc поля или константы должен раскрывать **назначение, смысл значения и особенности его использования**, а не повторять название или тип.

Документация должна отвечать на вопросы:

- Что означает значение? / Для чего оно используется?
- В каких ситуациях применяется?
- Какие ограничения или единицы измерения имеет?
- Как значение влияет на поведение компонента?

Примеры:

```java
// плохо, так как описание повторяет название константы:
// непонятно, к чему относится таймаут
// и что произойдёт при его превышении

/**
 * Таймаут.
 */
private static final Duration CONFIRMATION_TIMEOUT =
        Duration.ofSeconds(30);


// хорошо, так как раскрывает назначение,
// единицу измерения и влияние на поведение

/**
 * Максимальное время ожидания ответа от внешнего
 * сервиса при подтверждении заказа.
 */
private static final Duration CONFIRMATION_TIMEOUT =
        Duration.ofSeconds(30);
```

Не требуется документировать каждое поле, если его назначение очевидно из названия и контекста.

Javadoc обязателен для публичных констант и енамов.

## Как писать и поддерживать javadoc

- Javadoc пишется на русском языке, если не указано обратное.
- При изменении поведения, контракта или ограничений компонента необходимо актуализировать его Javadoc.
- Первое предложение кратко описывает назначение компонента и заканчивается точкой.
- Дополнительные абзацы отделяются тегом <p>.
- Между основным описанием и тегами @param, @return, @throws оставляется пустая строка.
- Описания параметров выравниваются; длинные описания переносятся с дополнительным отступом.
- Для ссылок на классы, методы и поля используется {@link}.
- Для кода, литералов и значений (null, true, false) используется {@code}.
- Теги располагаются в порядке: @param, @return, @throws, @see, @deprecated.
- Неиспользуемые теги не добавляются.

Пример:

```java
// плохо, так как нарушены правила оформления Javadoc:
// - описание не раскрывает поведение метода и не заканчивается точкой;
// - отсутствует пустая строка перед тегами;
// - нарушен порядок тегов;
// - используется обычный текст вместо {@link} и {@code};
// - не выровнены описания параметров;
// - не указаны условия возникновения исключения;
// - документация не соответствует фактическому контракту
// - есть упоминание enum-значения, но не используется {@link ..}
// - есть упоминание имени класса, но не используется {@link ..}

/**
 * Обрабатывает заказ
 * Вызывает OrderValidatorService и сохраняет результат
 * @return заказ со статусом READY_FOR_EXECUTION
 * @throws IllegalStateException ошибка
 * @param order Order для обработки
 */
Order confirmOrder(Order order);


// хорошо, так как соблюдены правила оформления,
// описаны контракт метода и условия возникновения ошибки, используется {@link ..}

/**
 * Подтверждает заказ и переводит его
 * в состояние готовности к исполнению.
 * <p>
 * При успешном подтверждении сохраняет новое
 * состояние заказа и регистрирует
 * {@link OrderConfirmedEvent}.
 *
 * @param order заказ в состоянии
 *              {@link OrderStatusEnum#CREATED}
 * @return подтверждённый заказ в состоянии
 *         {@link OrderStatusEnum#READY_FOR_EXECUTION}
 * @throws IllegalStateException
 *         если состояние заказа не допускает подтверждение
 */
Order confirmOrder(Order order);
```
