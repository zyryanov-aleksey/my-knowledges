# Правила именования классов

## Основные понятия

По имени класса должно быть понятно, какую часть функционала приложения он представляет и к какой предметной области относится, не открывая его реализацию.

- Основу имени составляет сущность или концепт предметной области: `Order*`, `Payment*`, `UserRegistration*`.
- Каждый класс выполняет техническую или архитектурную роль - роль указывается явно: `OrderController`, `PaymentDto`, `UserRegistrationService`.
- Если класс отвечает за бизнес-операцию, лучше называть его через бизнес-смысл, например `PaymentService`. Если он отвечает за конкретную техническую реализацию - через эту реализацию, например: `PaymentRepository`, `OrderRepository`.

Следует избегать абстрактных ролей при именовании класса, даже если похожих в реализации не планируется, например, хорошие названия - `OrderCancellationService`, `UserRegistrationService`, `BiometryValidationService`, так как явно сообщает программисту зачем нужен этот сервис.

## Суффиксы классов

Необходимо использовать одинаковые суффиксы с одинаковым смыслом по всему проекту

- `...Configuration` для создания конфигурационных классов приложения, безопасность, подключение к БД, интеграция с другими сервисами
- `...Properties` для создания проперти-классов
- `...Controller` для класса и `...Api` для интерфейса. Используются для обработки входящих запросов по http (rest, grpc, etc...)
- `...Service` и `...ServiceImpl` Сервисный слой содержит бизнес-логику
- `...Repository` репозитории взаимодействуют с базой данных.
- `...Entity` сущность для представления данных БД в виде сущностей
- `...Dto`, `...RequestDto`, `...ResponseDto` для DTO внешних API и интеграционных контрактов
- `...Domain` для каких то доменных объектов с которыми работают обслуживающие слои
- `...Handler` для перехвата вызовов, например `grpc server handler`, `error handler`, etc
- `...Exception` для специализированной обработки возникающих ошибок
- `...Mapper` мапперы преобразуют сущности в DTO и наоборот
- `...Util` классы со статическими вспомогательными методами
- `...Type`, `...Enum` классы содержащие константы, enum-классы
- `...Converter` для конвертации данных, например из БД (`org.springframework.core.convert.converter.Converter`)
- `...Interceptor` используется только в контексте `gRPC`, например `ProtoValidationInterceptor`
- `...Scheduler` периодический планировщик задач, например `HealthStateScheduler`

**Обязательное правило - при написании кода использовать только вышеперечисленные суффиксы**
