## Введение в skill-generator

Данные файлы/скрипты/код предназначены для конвертации имеющихся знаний в скиллы, которые сможет использовать агент при разработке ПО.

Суть заключается в том, чтобы преобразовать имеющиеся человекочитаемые знания в агенточитаемые скиллы.

## Правила написания кода

### Форматирование кода

При выполнении задач связанных с написанием кода необходимо следовать правилам форматирования кода и использовать автоформатирование каждого файла, измененного в рамках агентской сессии. Если активен intellij idea mcp server, то использовать инструмент `Formatting Tool` для измененного файла (Документация: https://www.jetbrains.com/help/idea/mcp-server.html#formatting-toolset).

Порядок работы при любом изменении:

1) Любое внесение изменения в код
2) Вызов инструмента автоформатирования для каждого измененного файла отдельно
3) Проверка что все изменения соответствуют правилам описанным в скиле: $java-spring-framework-code-style
4) Исправление кода в соответствии с правилами скила
5) Вызов инструмента автоформатирования

Так же необходимо повторить порядок работы для соблюдения формата кода еще раз глобально для всех измененный файлов в рамках агентской сессии перед передачей результата выполненной задачи пользователю.

Примечание:

- Рекомендуется решать задачу по форматированию кода в рамках отдельного сабагент-ревьера, так как некоторые задачи по форматированию могут занимать много контекста.

### Кодстайл ревью

При выполнении задач связанных с написанием кода после изменения файлов проекта необходимо вызывать автоматическое статическое ревью написанного кода. Для этого используется инструмент checkstyle с помощью gradle, а так же intellij idea mcp server и его инструмент `get_file_problems` (Документация: https://www.jetbrains.com/help/idea/mcp-server.html#get_file_problems)

Порядок работы при любом изменении (обязательно после этапа форматирования кода):

1) Получение измененных файлов в рамках сессии
2) Применение checkstyle глобально с помощью gradle
3) Исправление checkstyle ошибок
4) Применение `get_file_problems` и анализ ошибок для каждого измененного файла по отдельности (не только error, но и warnings и другие менее важные предупреждения)
5) Исправление всех ошибок возникших после анализа `get_file_problems`
6) Инициация повторного форматирования кода после изменений

Примечание:

- Если `get_file_problems` показывает предупреждение или ошибку, но участок кода не является ошибочно написанным или осознанного отошедшим от правил написания кода, то следует пометить либо класс, либо метод как игнорирующим ошибку с помощью @SuppressWarnings(...) аннотации (обязательно либо на уровне класса либо метода).
- Рекомендуется решать задачу по соблюдению кодстайла в рамках отдельного сабагент-ревьера, так как некоторые задачи по соблюдению кодстайла могут занимать много контекста. Если в рамках исправлений для соблюдения кодстайла понадобится изменить несколько классов, то передать это заключение в основной поток для согласования изменений и принятия решения по исправлению

## Указания для агента

- Использовать суб-агентов:
    - в рамках рабочей сессии необходимо использовать различных суб-агентов для экономии контекстного окна
    - субагент должен решать одну конкретную небольшую задачу, если решение задачи требует множества изменений, то рекомендуется создавать несколько агентов с одинаковой ролью чтобы они полностью были погружены в одну небольшую часть задачи
    - минимальный набор суб-агентов:
        - агент-архитектор для планирования изменений в рамках задачи и проверки соблюдения всех условий другими агентами
        - агент-разработчик-программист для написания основного кода
        - агент ревьюер для проверки и соблюдения правил написания кода
        - агент тестировщик для написания и поддержки тестов у написанного кода
        - и другие агенты необходимые для выполнения задачи по усмотрению исполнителя
- Пока что сервиса нет на прод, поэтому рекомендуется не создавать новые ликвибейз-скрипты, а редактировать уже имеющийся скрипт номер 1
- Пока что сервиса нет на прод, поэтому рекомендуется НЕ соблюдать правила обратной совместимости в протобаф протоколе
- Не изменять схемы и не изменять документацию сервиса если того не просит пользователь, если необходимо изменить - то согласовать с пользователем
